# Ecosystem Awareness — canonical corpus

> **Substantive corpus citation anchor (19 September 2026):** [`55fb4da3e5b6c54ecdffe7b12670e1edde408787`](https://github.com/dakleyer/structural-awareness-contributions/commit/55fb4da3e5b6c54ecdffe7b12670e1edde408787). `main` is the live public reading route; cite the full commit URL of the corpus version read for a stable reference.

Ecosystem Awareness (EA) asks whether the evidence, assumptions and available response behind **this decision** still justify its operating frame when the surrounding ecosystem is only partly known and changing. A locally correct agent, policy result or human approval need not establish a supported whole-system conclusion. More search, more agents or more review may consume the time and capacity needed to respond without resolving the material gap. EA therefore makes the observation boundary, residual uncertainty, source dependence and decision horizon explicit; qualifies what can be composed; and requests the smallest useful requalification when the frame changes.

This is the **single public reading folder for the EA corpus**. It contains the current architectural argument, candidate integration annexes, validation profiles, research lineage, conservation and governance records. These are distinct artefact types, not one article or one validated stack. The case and adjacent programmes retain their own corpora; EA links them rather than importing their source texts.

3. [00E — Reference Failure Scenario and Quality-Gate Plan: 100 Million Tokens](./00E_FAILURE_MODES_100M_TOKEN_COMPOUNDING_v0.1.md): the preserved five-stage source case operationalised as one concrete company with four coupled subsystems—production I2, quality-control/human I1 with a possible forced I2 closure, strategy O2 and deployment O1. It explains the many-to-one information-loss mechanism, defines a matched-resource comparator, and traces scope → S# → T# → H# → KPI → deterministic gate disposition → outcome through the non-conforming and requirements-conforming quality routes. An unresolved limit may be carried explicitly without an online Type-0 diagnosis; Type 1/2 gate breaches may not advance.
   - [00E-A01 — Microsoft Agent 365 implementation profile](./00E_A01_MICROSOFT_AGENT_365_IMPLEMENTATION_PROFILE_v0.1.md): the first product-implementation annex. It shows how documented registry, identity, security, compliance and observability capabilities can materially mitigate the case when well implemented, then stresses an excellent implementation with a latent regime change. T1/H5 and T4/H6 distinguish operational control from automatic epistemic requalification; T3/PNI is retained as a bounded response constraint. It is neither a benchmark nor a claim of product inadequacy.
   - [00E-A02 — LangGraph/LangSmith implementation profile](./00E_A02_LANGGRAPH_LANGSMITH_IMPLEMENTATION_PROFILE_v0.1.md): the orchestration-runtime annex. It compares a standard graph, a top stateful/observable/evaluated implementation and the same top implementation after a latent regime change. It tests T1/H5 and T4/H6 under finite human capacity and keeps T3/PNI bounded. It is neither a product ranking nor a claim that durable execution or human-in-the-loop is inadequate.
4. [00F — Reference Failure Scenario: Smart-City Mobility Divergence](./00F_FAILURE_MODE_SMART_CITY_MOBILITY_SYSTEMIC_DIVERGENCE_v0.1.md): the second technology-neutral reference scenario. A fictional multi-actor mobility ecosystem receives noisy, stale and partly dependent telemetry and diverges into Emergency Plan A, Emergency Plan B, NORMAL and HOLD. The document explains why the local closures may each be understandable, how their unqualified composition over one corridor becomes dangerous, and how Q0–Q5 map S#/T#/H#/KPI evidence to bounded containment and targeted requalification without creating a supercontroller.
   - [00F-A01 — FIWARE NGSI-LD / Orion-LD implementation profile](./00F_A01_FIWARE_NGSI_LD_IMPLEMENTATION_PROFILE_v0.1.md): the first smart-city technology annex. It compares a standard context-broker implementation, a top federated/temporal/monitored implementation and that same top implementation after a gradual or initially unknown regime pivot. It shows how strong implementation materially reduces the risk while T1/H5 and T2/T4/H2/H4/H6 still require decision-scoped requalification and bounded composition. It is neither a product benchmark nor a claim that FIWARE causes the failure.
   - [00F-A02 — AWS IoT TwinMaker / IoT Core implementation profile](./00F_A02_AWS_IOT_TWINMAKER_CORE_IMPLEMENTATION_PROFILE_v0.1.md): the second smart-city technology annex. It compares a standard IoT/digital-twin/event implementation, a top governed and monitored implementation and that same implementation after a hidden dependency, timestamp-semantic and model-validity pivot. It keeps safety actuation outside TwinMaker in accordance with the documented product boundary and tests T1/H5 and T2/T4/H2/H4/H6. It is neither a benchmark nor a claim that AWS technology causes the failure.
5. [Concrete candidate architecture — 00 topology](./00_CANONICAL_ARCHITECTURE_TOPOLOGY.md), followed by 01–05 below: EA's specific conceptual, functional and interface design.
6. [00D — Canonical Architecture Benchmark and Reference-Scenario Evidence](./00D_CANONICAL_ARCHITECTURE_BENCHMARK_AND_REFERENCE_SCENARIO_EVIDENCE_v0.2.md): the single benchmark route. It integrates EA-H1–EA-H4, B0–B3 fair comparison, existing agent benchmarks and primary-source corroboration of the mechanisms in 00E/00F. It distinguishes formal results, controlled experiments, investigated occurrences and market/standard evidence, and states exactly what each source does and does not establish.
   - [00D-A01 — Reference-Scenario Test Artifacts and Bounded Reference-Oracle Proof Sketch](./00D_A01_REFERENCE_SCENARIO_TEST_ARTIFACTS_AND_BOUNDED_ORACLE_PROOF_SKETCH_v0.1.md): companion evidence-design annex for readers who need to turn the fictional scenarios into reproducible fixtures. Its traceability matrix, bounded deterministic oracle, controls, public commit-anchored pre-registration before execution and Stage 0–2 progression make the already-declared regime-change/residual boundary testable rather than implicit. It is a plan for test construction, not an executed testbed, validation or claim that EA has passed.
   - [00D-A02 — Stage-0 Execution and Coverage-Alignment Change Plan](./00D_A02_STAGE_0_EXECUTION_AND_COVERAGE_ALIGNMENT_CHANGE_PLAN_v0.1.md): dated public record of the enacted fixture, KPI, coverage-map and S14-alignment changes. It is not an execution result; the next substantive artifact is a pre-registered Stage-0 fixture and its trace.
   - [00D-A03 — RS-00E-Q1a Stage-0 Deterministic Harness Design](./00D_A03_RS_00E_Q1A_STAGE_0_DETERMINISTIC_HARNESS_DESIGN_v0.1.md): a deliberately bounded implementation design for one common-dependency fixture family and its negative control. It is a reproducible-harness design only; the required next evidence artifact remains its public pre-registration and then its trace.

Across this route, Type 1 and Type 2 remain the only operational management-failure classes. False convergence, incompatible divergence, defensive `UNKNOWN`, qualifier saturation, induced doubt, oscillation and cascade are recorded as mechanisms, transitions or consequences and are measured through the existing H1–H6 and KPI route rather than promoted to new types or hypotheses.

Do not read the sequence backwards when assessing the claim: the architecture is not the requirement, and a requirement is not evidence that the architecture works.

The document in step 2 is the only canonical requirements document in this route. Earlier working inputs remain unchanged outside this route; their status and provenance are recorded in [non-canonical](./non-canonical/README.md).

## Research lineage

The five separately preserved articles show the derivation without replacing 01–06:

1. [I — Naturalistic foundations & agentic lifecycle inversion](./ARTICLE_01_NATURALISTIC_FOUNDATIONS_AND_AGENTIC_LIFECYCLE_INVERSION.md): distinguishes a protected system from its changing ecosystem of collaborators, competitors and adversaries. It examines faster agentic lifecycles and change without a central planner, then moves from protecting assets alone toward qualifying the assumptions on which operation depends. That shift motivates the minimum-sufficiency question.
2. [II — Minimum control & multi-optima](./ARTICLE_02_MINIMUM_CONTROL_ARCHITECTURE_MULTI_OPTIMA.md): starts with the owner-declared Objective Envelope, then examines resource allocation and the feasible region of sufficient control. Different C/P/M configurations and local or Pareto-efficient alternatives may coexist. It relates response capacity to warning, observation windows and signalling; it does not establish a single global minimum.
3. [III — Semantic Window & Good-Enough Early Warning](./ARTICLE_03_SEMANTIC_WINDOW_AND_GOOD_ENOUGH_EARLY_WARNING.md): derives the observation window backward from the objective, threat, reachable response and useful response time. Warning quality is assessed relative to action, not temporal width alone. It treats window failures, the relation to Regime Awareness and trade-offs among observation, warning and response capacity.
4. [IV — signalling without required cooperation](./ARTICLE_04_ECOSYSTEM_SIGNALLING_WITHOUT_REQUIRED_COOPERATION.part01.md) ([part 2](./ARTICLE_04_ECOSYSTEM_SIGNALLING_WITHOUT_REQUIRED_COOPERATION.part02.md)): studies signals among independently governed actors without assuming shared goals. Signal value is conditional; correlation is not corroboration; aggregation and Byzantine-resilience approaches have limits. It examines lifecycle, assurance, minimum semantics and privacy. Improved local knowledge creates neither global command nor global authority.
5. [V — FG-TIDA reference-model proposal](./ARTICLE_05_INTEGRATED_REFERENCE_MODEL_FOR_FG_TIDA.part01.md) ([part 2](./ARTICLE_05_INTEGRATED_REFERENCE_MODEL_FOR_FG_TIDA.part02.md), [part 3](./ARTICLE_05_INTEGRATED_REFERENCE_MODEL_FOR_FG_TIDA.part03.md)): brings together the objective → possible control → window → warning → signalling chain. It proposes vocabulary, minimum semantics, architectural properties, test profiles and interoperability questions for study, with links to Themes #13/#16 and explicit out-of-scope boundaries. Part 3 retains the institutional limit: this is a proposed work package, not an adopted group model.

The predecessor [Architectural Principles](./ARCHITECTURAL_PRINCIPLES_v0.1.md) and [Three Dimensions of Indeterminacy](./THREE_DIMENSIONS_OF_INDETERMINACY_WORKING_TECHNICAL_ARCHITECTURE.part01.md) ([2](./THREE_DIMENSIONS_OF_INDETERMINACY_WORKING_TECHNICAL_ARCHITECTURE.part02.md), [3](./THREE_DIMENSIONS_OF_INDETERMINACY_WORKING_TECHNICAL_ARCHITECTURE.part03.md), [4](./THREE_DIMENSIONS_OF_INDETERMINACY_WORKING_TECHNICAL_ARCHITECTURE.part04.md)) supply the earlier conceptual taxonomy.
